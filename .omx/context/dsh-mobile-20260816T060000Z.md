# DSH Mobile Context Snapshot

## Task

Build the Flutter 3.x mobile client in `dsh-mobile/` and keep it independently versioned.

## Desired outcome

An iOS 14+ and Android 8+ app that registers or logs in, pairs a computer, manages devices, and opens the remote DSH Web UI through the Relay ticket and Cookie flow.

## Known decisions

- Mobile only; Companion and Relay are owned by other tasks.
- Public contracts live under `dsh-公共文档/`.
- Email and password authentication; no verification or recovery in MVP.
- Flutter 3.x with `flutter_inappwebview`, `mobile_scanner`, `flutter_secure_storage`, and `dio`.
- Fixed light theme matching the supplied DSH product screenshot, not the dark marketing page.
- Current Relay behavior is the authoritative integration baseline.
- Local Mock mode is required so mobile development does not depend on Relay availability.

## Non-goals

- Push notifications, native approval cards, native chat UI, end-to-end encryption, multi-account switching, tablet layouts, and custom theme switching.

## Decision boundaries

The mobile implementation may choose Riverpod or Bloc, navigation structure, internal data models, test organization, and exact spacing within the DSH visual language. It must not change another application's source or expose device credentials to mobile.

## Acceptance evidence

- Format, analyze, unit/widget tests, iOS build, and Android build.
- Mock flow covers authentication, pairing, device list, rename, unbind, and WebView states.
- Real API adapter conforms to the implementation-aligned public contract.
